# 検証層の設計 — 証明支援系と AI をどう噛ませるか

対象: `mathrel-verify`（新規クレート）
関連文書: `企画書第3版.md` §6.1（カーネルとホストの責務分担）、§9 ADR-004（カーネルは評価しない）

---

## 0. 結論から

**証明の検証は、カーネルにとって「評価」と同型である。カーネルは変更しない。**

カーネルが知っているのは 2 つだけだった。

1. 誰が誰に依存しているか
2. いま何が古いか

`y = f(x)` が古くなるのと、`定理: f は単調である` が古くなるのは、**同じ現象**である。どちらも `f` に依存しており、`f` が変われば両方とも作り直しになる。したがって検証層は新しい追跡機構を必要としない。既存の `next_batch` → 評価 → `commit_evaluation` ループに、別種のバックエンドを挿すだけでよい。

この同型が成立するために必要なものは 1 つ、**証明の「指紋」を定義すること**である（§3）。

## 1. 解こうとしている問題

### 1.1 場面

`f(t) = t^2 + c` を定義し、「`f` は `t ≥ 0` で単調増加」を Lean で証明したとする。数日後、`c` の定義を変える。

このとき、証明は生きているか。

答えは「この場合は生きている」だが、**その判断をしているのは人間の頭の中だけ**である。ノートにも、Lean のファイルにも、「この証明は `c` の何に依存していたか」は保存されていない。`lake build` を回せば Lean は再検査するが、それは「ファイルが変わったから」であって、「数学的に何が影響を受けたか」ではない。

### 1.2 痛点

企画書 §1.2 の痛点 1（定義変更のコストが線形以上にかかる）は、証明が絡むと桁が変わる。

| | 再計算のコスト | 変更 1 回あたり |
|---|---|---|
| 算術評価 | マイクロ秒 | 全部やり直しても気づかない |
| CAS の記号計算 | ミリ秒〜秒 | 気になり始める |
| Lean の再検査 | 秒〜分（Mathlib 込みなら分〜十分） | **全部やり直しは非現実的** |

つまり**早期カットオフは、証明においてこそ本質的**である。カーネルが `MaybeDirty` と `Dirty` を分けている設計（`state.rs`）は、算術では最適化に過ぎないが、証明では成立条件そのものになる。

## 2. 中心的な主張: 検証は評価の一種である

### 2.1 対応関係

| 評価（既存） | 検証（新規） |
|---|---|
| セル `y = f(x)` | 検証義務 `thm: ∀t≥0, f(t) ≤ f(t+1)` |
| `requires: NameBound(f)` | `requires: FunctionBound(f/1)` |
| ホストが `eval` する | ホストが Lean を呼ぶ |
| `EvalOutcome::Value { digest }` | `EvalOutcome::Value { digest }` |
| `EvalOutcome::Failed { reason }` | 証明が通らなかった |
| `Dirty` | 定義が変わったので再検査が要る |
| 早期カットオフ | **定義の指紋が同じなら再検査しない** |

カーネル側に必要な変更は `Capability` に 1 つ変種を足すことだけである。`Capability` は `#[non_exhaustive]` であり、`relation.rs` に「この列挙は将来拡張される」と明記されている。

```rust
/// 命題が証明済みである。
PropositionProved(Symbol),
```

`定理 B` が `補題 A` を使うなら、`B.requires = [PropositionProved(A)]` と書く。これで補題を直したときに定理が `Dirty` になる。値の束縛（`NameBound`）と混ぜないのは、`A` という名前の値と `A` という名前の命題が同居できるようにするためである（`NameBound` と `FunctionBound` を分けたのと同じ理由）。

### 2.2 何がタダで手に入るか

カーネルを流用することで、以下は実装せずに手に入る。

- 定義を変えたとき、影響を受ける証明の特定
- 証明の依存順スケジューリング（補題を先に検査する）
- 循環依存の検出（`A` の証明に `B` を使い、`B` の証明に `A` を使っている）
- 未解決参照の検出（存在しない補題を引用している）
- 早期カットオフ（下記 §3 が前提）

## 3. 証明の指紋

早期カットオフが効くかどうかは、指紋の定義にすべてかかっている。

### 3.1 定義

検証義務 `O` の指紋を次で定める。

```
digest(O) = H( statement_canonical(O)
             ‖ backend_id ‖ backend_version
             ‖ verdict_tag
             ‖ trust_tag
             ‖ digest(u1) ‖ digest(u2) ‖ ... )     // u_i は O の上流（昇順）
```

上流の指紋を混ぜるのは、ホスト層が `f(t) = t^2 + c` の指紋を作るときに既にやっていることと同じである（`workspace.rs` の `Stmt::FuncDef` の扱い）。

### 3.2 これで何が起きるか

- `c = 1` を `c = 1` に「編集」した（実質変更なし）→ `c` の指紋が変わらない → `f` の指紋も変わらない → **定理は再検査されない**
- `c = 1` を `c = 2` に変えた → `c` の指紋が変わる → `f` の指紋が変わる → **定理は再検査される**
- Lean のバージョンを上げた → `backend_version` が変わる → **全証明が再検査される**（正しい挙動。ただしこれは指紋だけでは実現しない。§6.0(a) を参照）
- 証明本体（tactic script）だけを書き換えた → statement は同じ → **下流の定理は再検査されない**

最後のものが重要である。証明を書き直しても、**その定理を使っている他の定理は再検査しなくてよい**。定理の利用者が依存しているのは statement であって proof ではないからだ（proof irrelevance）。これは指紋に proof を含めないことで自動的に成立する。

### 3.3 SPEC-GAP

指紋に proof を含めないので、「証明が通っていないのに通ったことになる」経路がないかを確かめる必要がある。答えは `verdict_tag` を混ぜていることによる。証明が通っていなければ `verdict_tag` が `Proved` にならず、`Freshness::Clean` にもならない（`commit_evaluation` は `EvalOutcome::Failed` を受け取る）。

## 4. 信頼度 — AI をどこに置くか

### 4.1 唯一の防衛可能な配置

```
        提案する                       判定する
   ┌──────────────┐              ┌──────────────┐
   │  AI (Codex,  │  証明の候補   │  Lean 4      │
   │  Claude, …)  │ ───────────→ │  (kernel)    │
   └──────────────┘              └──────────────┘
          ↑                              │
          │  失敗したら理由を返して再挑戦   │ 通ったものだけ
          └──────────────────────────────┘
                                         ↓
                                  Verdict::Proved
```

**AI は探索ヒューリスティックであり、権威ではない。** AI が出した証明を Lean が拒否したら、それは単に失敗した試行である。この配置は LeanDojo / DeepSeek-Prover / AlphaProof が共通して採っているもので、他の配置に防衛可能なものはない。

### 4.2 しかし、それだけでは足りない

現実には「Lean で完全に証明する」以外の状態が要る。

- `axiom` や `sorry` を置いて先に進む（数学の作業では普通のこと）
- AI に「この補題は多分成り立つ」と言わせて仮置きする
- 人間が「これは既知」と宣言する

これらを禁止すると使い物にならない。許すと健全性が崩れる。**解決は、禁止でも放置でもなく、信頼度を第一級にして依存に沿って伝播させることである。**

### 4.3 信頼度の束

```rust
pub enum Trust {
    Checked,    // 証明支援系が検査した
    Assumed,    // 人間が「既知」と宣言した
    Suggested,  // AI が主張した。誰も検査していない
    Unknown,    // 何も分かっていない
}
```

順序は `Checked > Assumed > Suggested > Unknown` である。

**実効信頼度 = 自分の信頼度 と 全上流の実効信頼度 の下限（meet）。**

```
effective(O) = min( own(O), min over u in upstream(O) of effective(u) )
```

これが本設計の核心である。Lean が完全に検査した定理でも、AI が仮置きした補題に依存していれば、実効信頼度は `Suggested` にしかならない。「Lean が通ったから正しい」という誤った安心を、構造的に防ぐ。

そして**この計算に必要な依存グラフは、カーネルが既に持っている**。新しいグラフは要らない。

### 4.4 帰結

- ワークスペース全体の信頼度は「最も弱い環」で決まる。UI はこれを 1 行で出せる。
- AI に補題を仮置きさせて先に進むのは自由。ただし、それに依存する全部が黄色くなる。
- 仮置きを本物の証明に置き換えると、下流の実効信頼度が自動的に上がる。**このとき下流の再検査は不要である**（statement は変わっていないので指紋も変わらない）。信頼度の再計算だけで済む。

## 5. バックエンド

```rust
pub trait Verifier {
    /// 検証器の同一性。指紋に混ざる。
    fn backend(&self) -> BackendId;
    /// `context` には上流の定義と、引用した補題の `axiom` 宣言が依存順に入る。
    fn verify(&self, obligation: &Obligation, context: &[String]) -> Verdict;
}
```

| 実装 | 役割 | 状態 |
|---|---|---|
| `Trivial` | 構文的に自明なものだけ通す。テストと自己診断用 | 実装 |
| `Lean` | 一時ファイルへ書き出し `lake env lean <path>` を呼ぶ。`#print axioms` で `sorry` を検出する | 実装（プロセス起動は注入可能） |
| （仮置き） | 人間の宣言。検証器ではなく `ProofSpace::add_assumption` で表す（§6.0(f)） | 実装 |
| SMT (z3/cvc5) | 決定可能な断片を投げる | P4 以降 |

Lean バックエンドはプロセス起動を trait 越しにしてある。Lean が入っていない環境でも、出力の解釈をテストできるようにするためである（実際、この設計時点の開発機に Lean は入っていない）。Lean が見つからなければ `Verdict::Unavailable` を返し、**`Refuted` とは区別する**。道具がないことと、偽であることは別である。

### 5.1 AI の口

```rust
pub trait ProofSynthesizer {
    fn propose(&self, obligation: &Obligation, feedback: &[Attempt]) -> Option<String>;
}
```

`feedback` に過去の失敗（Lean のエラー出力）を渡す。これが探索ループになる。

```
propose → verify → 失敗ならエラーを添えて propose → ... （上限回数まで）
```

`CodexSynthesizer` は `codex exec` を叩く実装である。**判定は一切しない。** 返すのは証明の候補文字列だけであり、それが正しいかは `Verifier` が決める。

## 6. どこまで出来るか

正直な見積もりを 4 段階で置く。各段に「成功条件」と「そこで詰まる理由」を書く。

### 段階 1: 依存追跡だけ（実装済みの延長）

証明を「不透明な検証済みフラグ」として扱い、定義が変わったら赤くする。Lean も AI も要らない。

- **成功条件**: `c` を変えたら、`c` に依存する定理だけが「要再検査」になる。
- **価値**: これだけでも、現状（誰も追跡していない）より確実に良い。
- **限界**: 「要再検査」と言われても、再検査するのは人間である。

### 段階 2: Lean の自動再検査

要再検査になったものを、依存順に `lake env lean` へ投げ直す。

- **成功条件**: 定義変更後に「まだ通る証明」と「壊れた証明」が自動で分かれる。
- **詰まる理由**: **statement を Lean の構文へ翻訳する部分**である。ここが本当の難所であり、パーサでもカーネルでもない。`f(t) = t^2 + c` から `def f (t : ℝ) : ℝ := t^2 + c` を作るのは、型（`ℝ` か `ℕ` か）を決める必要があり、それは企画書 R4（CCE の型制約）と同じ問題の再来である。
- **現実的な落とし所**: v0.1 では**翻訳しない**。ユーザが Lean のコードを直接書き、mathrel は依存関係と再検査のスケジューリングだけを持つ。翻訳の自動化は段階 4。

### 段階 3: AI による証明の下書き

壊れた証明を AI に直させる。失敗したら Lean のエラーを添えて再挑戦。

- **成功条件**: 定義変更で壊れた証明のうち、一定割合が人手を介さず直る。
- **期待値の見積もり**: 「定数を変えたので `norm_num` の数値が合わなくなった」程度なら高確率で直る。証明の構造が変わる変更は難しい。**公開ベンチマーク（miniF2F 等）の数字をそのまま期待してはいけない。** あれは「新規に証明する」課題であり、こちらは「既存の証明を変更に追随させる」課題で、性質が違う。むしろ後者の方が易しい可能性がある（元の証明という強い事前情報がある）。これは測る価値のある仮説である。
- **詰まる理由**: AI の 1 回の試行に数十秒〜数分かかる。定義を 1 つ変えて 20 個の証明が壊れたら、直列では実用にならない。**カーネルの `next_batch` が並列化の単位を与える**ので、ここは設計上有利である。

### 段階 4: 双方向（Lean ↔ mathrel）

Lean 側のファイルを正とし、mathrel が依存グラフを導出する。あるいは逆。

- **成功条件**: 既存の Lean プロジェクトを取り込んで、その依存グラフを mathrel で見られる。
- **詰まる理由**: これは既に `lake` と `LeanDojo` がやっている領域である。**車輪の再発明になる。** やるなら、mathrel 独自の価値（計算と証明が同じグラフに載る）が出る部分に絞るべきである。

### 6.0 外部レビューで判明した誤り（Codex）

Codex に検証層のレビューを投げたところ、**本文書の主張のうち 2 つが偽**（(a) と (b)）で、ほかに 4 つの穴が見つかった。いずれも修正済みで、それぞれ回帰テストを置いてある。

**(a) §3.2 の「Lean のバージョンを上げたら全証明が再検査される」は成立していなかった（重大度: 高）**

指紋に `backend_version` を混ぜても、カーネルはそれを知らない。`verify_all` は `next_batch()` が返したものしか処理せず、全部 `Clean` なら 1 件も回らない。**版を上げても何も起きなかった。**

対処: `ProofSpace` が直近に使った `BackendId` を覚え、変わっていれば全義務を明示的に古くする。回帰テストは `upgrading_the_backend_rechecks_everything`。

**(b) `lean --stdin` という呼び出し方は存在しない（重大度: 高）**

Lean 4 の `lean` はファイルを引数に取る。標準入力からソースを読ませる方法はない。既定値が端的に間違っていた。

対処: 一時ファイルへ書き出し、パスを引数に渡す。既定は Mathlib を使う前提の `lake env lean <path>`。import をビルドしてから走らせるなら `lake lean <path>`。

**(c) `sorry` の検出を警告文字列に頼るのは危険（重大度: 高）**

`declaration uses 'sorry'` の文字列一致に頼ると、文言・引用符・Lean の版・ラッパの介在で壊れる。しかも壊れたときに**`sorry` 入りの証明が `Checked` になる**ので、失敗の向きが最悪である。

対処: 生成ソースの末尾に `#print axioms <名前>` を置き、出力に `sorryAx` が現れるかを見る。これは Lean のカーネルが記録している公理依存であって文言ではない。加えて、証明を持たない義務（`sorry` を置いたのがこちら側の場合）は出力を見るまでもなく `Checked` にしない。警告文の一致は保険として残す。

**(d) 生の `verdict` と統計が「検証済み」を過大表示する（重大度: 高）**

`VerifyStats` が `Assumed` を `proved` に数えていた。消費側が「成立 N 件」とだけ表示すれば、仮置きが検査済みに見える。

対処: `checked` と `assumed` に分離。合算が要るときは `proved()` を呼ぶ。

**(e) 定義の本文に `axiom` を書けば信頼度追跡を素通りできる（重大度: 高）**

定義は検証器へ渡らず、無条件に `Checked` として扱われる（定義は主張ではないため）。しかし本文は任意のソースなので、そこが抜け道になる。

対処: 本文に `axiom` / `sorry` が現れたら、その定義の信頼度を `Assumed` に落とす。構文の一致による粗い検出であり取りこぼしはあるが、外す方向は常に「信頼度を下げる」側なので健全性は損なわれない。本質的な対策は定義も検証器に通すことであり、P3 の課題とする。

**(f) 仮置きを検証器の差し替えで表現していた（設計の誤り）**

`AssumptionVerifier`（何でも `Assumed` で通す検証器）を用意していたが、これは誤りだった。「人間が既知と宣言した」は**義務そのものの属性**であって、どの道具で検査するかとは無関係である。検証器で表現すると、(a) の一括再検査が仮置きの記録まで消してしまう。

対処: `AssumptionVerifier` を削除し、`ProofSpace::add_assumption` / `promote_assumption` に置き換えた。

**受け入れた指摘のうち、対処しないもの**

依存関係（`uses` / `cites`）が自己申告であることは指摘のとおりだが、これはカーネルの原則（依存の推測を禁じる）から来る意図的な設計である。ただし失敗の向きは悪くない。申告漏れがあれば、その名前は検査時の文脈に入らないので Lean が `unknown identifier` で落ちる。**危険なのは、申告漏れの名前が Mathlib の同名の定理に解決されてしまう場合**であり、これは本文書の限界として記録する（§6.2-5）。

### 6.1 実装して分かったこと（テストが暴いた 2 点）

**(a) 定義の指紋には上流を混ぜなければならない。**

`def f (t) := t + c` の本文は、`c` を書き換えても変わらない。本文だけで指紋を作ると `f` の指紋が据え置きになり、早期カットオフが「`f` は変わっていない」と判断して、`f` に依存する証明を `Clean` のまま残す。これは最適化の効きすぎではなく**健全性の穴**である。§3.1 の式で上流の指紋を混ぜているのはこのためであり、実装では `ProofSpace::definition_digest` がこれを行う。回帰テストは `changing_a_definition_rechecks_the_proofs_that_depend_on_it`。

**(b) 証明を書き直すと、直接の引用元が 1 回だけ巻き込まれる（未解決）。**

proof irrelevance により、命題が同じなら指紋は変わらない。したがって引用元を再検査する必要はない。ところがカーネルは、変更点の**直接下流を無条件に `Dirty`** にする（`kernel.rs` `propagate_from`）。指紋が変わったかは評価してみないと分からないので、保守的に倒しているのである。結果、証明を 1 行整形しただけで、直接の引用元が 1 回再検査される。2 段目より先は `MaybeDirty` に留まり、早期カットオフが救う。

算術ではこの 1 回は誤差である。Lean では秒〜分になる。

**改善案**: 変更時に直接下流も `MaybeDirty` にし、`Dirty` への昇格は `commit_evaluation` 時の指紋比較（`promote_downstream`）だけに任せる。これは健全である。`next_batch` は `MaybeDirty` も候補に含むので取りこぼさず、指紋が変われば `promote_downstream` が昇格させ、変わらなければカットオフが救う。現在より厳密に精度が上がる。

**未実施の理由**: カーネルの 2 段階伝播は `kernel.rs` に意図として明記されており、シナリオテスト T03〜T05 と性質テスト P6（精度）がこの振る舞いを固定している。検証層の都合でカーネルの規定を変えるのは、P0 の完了条件を書き換えることになる。**P1.5 の実測で、この 1 回分が実際に問題になるかを見てから決める。**

### 6.2 出来ないこと（はっきり書く）

1. **statement が正しいかは検証できない。** Lean が通すのは「書かれた命題が証明できること」であって、「書かれた命題が意図した主張であること」ではない。定式化の誤りは検出できない。これは Lean の限界であって、本設計の限界ではないが、利用者に誤解させてはならない。
2. **`Trust::Assumed` の中身は検証しない。** 人間が「既知」と言ったものは、そう記録するだけである。
3. **指紋の粒度以上の精度は出ない。** `f` の定義を「意味を変えずに」書き換えると指紋は変わり、下流は再検査される。数学的に同値かどうかの判定は、それ自体が定理証明である。偽陽性はここに残る。
4. **申告漏れの依存が、Mathlib の同名定理に解決され得る。** `uses` / `cites` は自己申告である（カーネルの原則で、依存の推測は禁じている）。申告し忘れた名前は検査時の文脈に入らないので、通常は Lean が `unknown identifier` で落ちる。**ただしその名前が Mathlib に存在すると、そちらに解決されて通ってしまう。** 依存グラフには現れないので、再検査も信頼度の合成も漏れる。対策は未定である。

5. **Mathlib の版に依存する。** `backend_version` に Mathlib のリビジョンを含めれば健全側に倒れるが、Mathlib を更新するたびに全証明が再検査になる。これは正しいが高価であり、実運用では緩和策が要る（未解決）。

## 7. 段階計画への組み込み

企画書 §8 に対して、次のように置く。

| フェーズ | 内容 | 状態 |
|---|---|---|
| P0 | カーネル v0.1 | 完了（T01〜T15、P1〜P6 が green） |
| P1 | 評価ループ + CLI | 完了（`mathrel --demo`） |
| **P1.5** | **検証層の骨格**（本文書 §2〜§5、段階 1） | **骨格は完了。**`ProofSpace` の依存追跡・早期カットオフ・信頼度伝播が統合テストで green |
| P2 | UI 最小 | 未着手（wasm ABI は用意済み） |
| P3 | Lean バックエンドの実地投入（段階 2） | 未着手。`LeanVerifier` は書けているが、Lean を入れた環境で回していない |
| P4 | AI 証明修復（段階 3） | 未着手。`repair` ループと `CodexSynthesizer` は書けているが、修復率を測っていない |

P1.5 で「骨格は完了」と言えるのは、以下がテストで固定されているからである。

- 定義と証明が 1 つのグラフに載る（`definitions_and_proofs_share_one_dependency_graph`）
- 定義を書き換えても内容が同じなら証明は 1 つも再検査されない（`rewriting_a_definition_to_the_same_text_rechecks_nothing`）
- 内容が変われば連鎖の末端まで再検査される（`changing_a_definition_rechecks_the_proofs_that_depend_on_it`）
- 信頼度が連鎖の全長にわたって落ちる（`weakness_propagates_the_whole_way_down`）
- 仮置きを本物に置き換えると下流の実効信頼度が上がる（`replacing_an_assumption_with_a_real_proof_lifts_everything_downstream`）

**測っていないもの**: 実際の Lean 起動、実際の再検査時間、AI の修復率。これらは P3 / P4 の課題であり、現時点で数字を主張してはならない。

P1.5 を P2 の前に置くのは、**信頼度の表示が UI 設計に影響するから**である。後から足すと、セルの状態表示を作り直すことになる。

## 8. 決定記録

### ADR-006: カーネルを変更せず、検証を評価の一種として扱う

**決定**: 検証専用の状態機械を作らない。`Capability::PropositionProved` を 1 つ足すのみ。

**理由**: 別の追跡機構を作れば、2 つのグラフの整合を取る責任が生まれる。`f` が変わったときに「値の依存」と「証明の依存」の両方を更新し、両者が食い違わないことを保証しなければならない。1 つのグラフなら、その問題自体が存在しない。

**再検討条件**: 証明の依存が値の依存と本質的に異なる粒度を要求することが分かった場合。

### ADR-007: AI は提案のみ。判定はしない

**決定**: `ProofSynthesizer` は文字列を返すだけで、`Verdict` を返せない。型で保証する。

**理由**: 型で分けておかないと、いつか「AI が高確度で正しいと言ったから通す」経路が生える。

**再検討条件**: なし。これを緩めるなら本設計は破棄される。

### ADR-008: 信頼度は下限で伝播する

**決定**: `effective(O) = min(own(O), min over upstream)`。

**理由**: 「Lean が通った」という表示が、AI の仮置きに依存していても出てしまうと、この道具は害になる。健全側へ倒す。

**再検討条件**: 利用者が「実効信頼度が下がりすぎて使えない」と言った場合。ただし対処は伝播の緩和ではなく、仮置きを減らす方向であるべきである。
