## 0. エグゼクティブサマリ

**作るもの**: 数式・定義・宣言を相互依存する数学オブジェクトとして管理する数学ワークスペース。中核は Relational Math Kernel（以下カーネル）。

**解く問題**: 数学作業では、定義を 1 つ変えると、それに依存する計算がすべて古くなる。現状、この「どこが古くなったか」を追跡しているのは人間の頭だけである。紙のノートにも、LaTeX にも、Jupyter にも、この情報は保存されない。

**やり方**: 数式を文字列ではなく、requires / provides を持つオブジェクトとして登録する。そこから依存グラフを導出し、変更が波及する範囲を機械的に特定する。

**やらないこと**: 新しい CAS を作らない。TeX 処理系を作らない。Python を置き換えない。計算は既存資産（CCE / SymPy / SageMath）に投げる。

**現在地**: カーネル v0.1 の要件定義が完了。実装未着手。

**最初の分岐点**: P0（カーネル単体）完了時点で、「定義変更 → 影響範囲特定」がデモとして成立するかを見る。成立しなければ、そこで方針を再検討する（§8 の中止基準）。

## 1. 解こうとしている問題

### 1.1 場面

想定する利用者は、理工系の学部後半から大学院、および実務で数式を扱う技術者である。特徴は次の通り。

- 手計算のノートと計算機の両方を使う
- 数式は書けるが、Python を書くのは目的ではなく手段である
- 1 つの問題に対して、定義・補助式・検算・可視化が積み上がる作業をする

### 1.2 現状で起きていること

第2版では「隙間を埋める」と書いていたが、その隙間を具体化する。次の 4 つが実際の痛点である。

**痛点 1: 定義変更のコストが線形以上にかかる**

ノートに 30 行の計算があり、5 行目の定数を変えたとする。6 行目以降のうち、どれが影響を受けるかは目で追うしかない。実際には影響を受けないものも多いが、それを判別するのに全部読み直すことになる。

**痛点 2: 記号の意味が保存されない**

LaTeX で書いた `\|v\|` は、ファイルの中では文字列である。3 ヶ月後の本人にも、計算機にも、それがベクトルノルムなのか絶対値なのか作用素ノルムなのかは分からない。分かるのは文脈を読んだ人間だけである。

**痛点 3: 数式から計算コードへの翻訳が毎回手作業になる**

`\int_0^1 x^2 dx` から `sympy.integrate(x**2, (x, 0, 1))` への変換は機械的である。にもかかわらず毎回人がやり、しかも数式側を直したらコード側も直す二重管理になる。

**痛点 4: 検算の鮮度が記録されない**

「この式は数値検証済み」「この式は変更後まだ検証していない」の区別は、どのツールにも保存されない。結果として、変更のたびに全部検証し直すか、検証を諦めるかの二択になる。

### 1.3 この 4 つの関係

痛点 1 と 4 は同じものの表裏である。どちらも「変更が何を古くしたか」の問題であり、依存関係の追跡で解ける。痛点 2 は意味情報の保持、痛点 3 は意味情報からの変換で解ける。

つまり、**依存追跡**と**意味保持**の 2 つが技術的な核である。カーネルはこの 2 つを担う。

### 1.4 なぜ既存ツールで解けないか

| ツール | 数式表現 | 依存追跡 | 意味保持 |
|---|---|---|---|
| LaTeX | 得意 | なし | なし |
| Jupyter | 弱い | セル順のみ | 変数名だけ |
| Pluto.jl / marimo | 弱い | あり | 変数名だけ |
| SymPy | 中 | なし | 式の構造まで |
| Mathematica | 得意 | 部分的 | 式の構造まで |
| Lean / Mathlib | 得意 | あり（強い） | 完全 |

Lean は依存も意味も持っているが、日常的な計算の入口としては重い。定理を証明するための道具であって、演習問題を解きながら数値検証する道具ではない。

空いているのは、**LaTeX 並みに書きやすく、Pluto.jl 並みに反応し、SymPy 並みに計算できる**位置である。ただしこれは「空いているから作れる」を意味しない。空いている理由が「難しいから」である可能性を、§7 で検討する。

## 2. 提案

数式・定義・写像・型宣言・意味マクロ・計算結果を、相互依存する数学オブジェクトとして管理する数学ワークスペースを作る。

一言で言えば、**数式オブジェクトのスプレッドシート**である。

表計算ソフトでは `A2 = A1 + 3` としたとき、A1 を変えれば A2 が更新される。これを、値だけでなく、定義・関数・型・ドメイン・意味マクロにまで拡張する。

```
x = 2
f(t) = t^2 + 1
y = f(x)

v : Vector[Real]
n = \norm{v}
```

このとき、ワークスペースは次を知っている。

- `x` は名前 `x` の束縛を提供する
- `f` はアリティ 1 の関数束縛を提供する
- `y` は `x` と `f` の束縛を要求する
- `v` は型 `Vector[Real]` を提供する
- `\norm{v}` は `v` の型に依存して `VectorNorm(v)` と解決される

したがって次が可能になる。

- `x` を変えると `y` が古くなる
- `f` を消すと `y` に未解決参照が立つ（`y` は消えない）
- `v` の型を `Real` に変えると `\norm{v}` の意味が `Abs(v)` に変わる
- `v` の型が未指定なら「型を指定してください」と言える

## 3. Relational Math Kernel

### 3.1 責務

カーネルが知っているのは 2 つだけである。

1. 誰が誰に依存しているか
2. いま何が古いか

カーネルは**評価しない。パースしない。数式の意味を解釈しない**。計算は上位層が行い、結果をカーネルに報告する。

この線引きは v0.1 要件定義書での決定であり、本企画書もこれに従う。理由は §9 ADR-004 に記す。

### 3.2 データモデル

```
Entity            数学オブジェクトの identity
Component         Entity に付随するデータ（式・型・表示・評価状態）
Relation          requires / provides
DependencyGraph   Relation から導出される依存グラフ
Scheduler         変更に応じて状態を更新し、再計算順序を提示する
```

Entity Component System に Relation を加えたものなので、**Relational ECS** と呼ぶ。

### 3.3 依存グラフを一次データにしない

重要な設計方針である。

```
数式本体・構成情報・意味情報
  ↓
requires / provides
  ↓
DependencyGraph
```

依存グラフは「現在の意味状態から見た派生ビュー」である。式の変更・定義の削除・型宣言の追加によって、依存関係を局所的に更新できる。

ただし**導出であることと、毎回再計算することは別である**。編集のたびに全再構築すると O(n) が毎回かかる。増分保守は必須であり、これは要件定義書 §7.2 で規定済みである。

### 3.4 状態モデル

エンティティの状態は直交する 3 軸で持つ。単一の enum に潰さない。

| 軸 | 値 |
|---|---|
| Resolution | Resolved / Unresolved / Ambiguous |
| Freshness | NeverEvaluated / Clean / MaybeDirty / Dirty |
| CycleFlag | in_cycle: bool |

`MaybeDirty` を分けているのは早期カットオフのためである。上流が変わっても値が変わらなければ、下流は再計算しなくてよい。これがないと偽陽性が溜まる（§7 R3）。

## 4. 先行研究と既存実装

第2版に欠けていた節である。**同じ問題は独立に 4 系統で研究されている**。

### 4.1 数学知識の関係モデル化

**OMDoc / MMT**（Kohlhase, Rabe ら, KWARC）が、カーネルとほぼ同じ層を狙っている。形式数学のための言語で、foundation-independence（基盤非依存）を重視し、theory を theory morphism で結んだ theory graph として知識を表現する。inclusion（継承相当）と view（既存 theory 間の接続）の 2 形態を持つ。

我々との違いは、MMT が証明系を向いているのに対し、我々は計算系を向いている点である。MMT の foundation-independence を計算バックエンドに対してやる、という位置づけができる。

### 4.2 変更影響解析（Change Impact Analysis）

**Autexier ら (2011), arXiv:1105.2392** が最も直接的な先行研究である。「MKM フォーマットがオブジェクト間の関係を明示的に表現している事実を使って、関連オブジェクトを計算し、変更がそれらにどう影響するかを予測する」— これは我々の「Relation から依存を導出して dirty にする」と同一の発想である。

実装は抽象化 → 伝播 → 射影の 3 フェーズ。規模感として、抽象化フェーズだけで 91 個の規則、伝播フェーズで 15 個の規則を要している。

**最重要の教訓**が 2 つある。

1. 形式的意味論を持たないため、変更が本当に影響するかを自動判定できない。「完全」であろうとすると可能性ベースで伝播せざるを得ず、**偽陽性が出る**
2. 編集のたびに即座に影響解析を走らせる方針は、著者が小さな編集を繰り返す場面では望ましくない

我々が最初にぶつかるのはアルゴリズムではなく偽陽性の量である、と読める。

関連して **Normen Müller, "Change Management on Semi-Structured Documents" (PhD thesis, Jacobs University Bremen, 2010)** が、この問題を正面から扱った博士論文として存在する。**未読。着手前に読むべき最優先の 1 本**である。

### 4.3 リアクティブノートブック

**Pluto.jl / Observable / marimo / ipyflow** が「値を変えたら依存先を再計算」を実装済みである。Pluto ではセルがノード、セル間の依存がエッジであり、ノートブックは有向マルチグラフとして表現される。

**Zheng ら (2025), "When Are Reactive Notebooks Not Reactive?", arXiv:2511.21994** が、これらの限界を 87 個のベンチマークで測定している。設計に直結する結果は次の通り。

| 変更の種類 | 結果 |
|---|---|
| 直接代入 | 全システムが正しく反応。ベースライン能力 |
| 再代入 | Marimo / Observable は静的に検出して実行拒否。IPyflow はタプルスワップ `a, b = b, a` で失敗 |
| ミューテーション | Rerun-All 以外、どのシステムも一貫した健全性を達成できず |
| ファイルシステム | Rerun-All 以外、非冪等なファイル変更に健全に反応したシステムはゼロ |

そして決定的な所見: **スコープを絞った系ほど精度が上がる**。直接代入テストでの再実行比率は Marimo / Observable がちょうど 1.00、IPyflow が 1.44。直接代入だけを考えればよいなら、値の変化は常に定義位置で起きるため、依存グラフの変化やリネージ追跡に関する多くのエッジケースが消え、静的解析だけで依存を追跡できる。

**これは我々にとって強い追い風である**。`x = 2` / `f(t) = t^2+1` / `y = f(x)` という宣言的な数学ワークスペースは、この「直接代入だけ」の世界にほぼ収まる。逆に、Python バックエンドを繋いだ瞬間にミューテーションと外部効果の世界に落ち、健全性が保証できなくなる（§7 R2）。

### 4.4 インクリメンタル計算の基盤

Rust で実装するなら **salsa** が事実上の標準である。input struct が外部から供給される可変状態、tracked struct が 1 つのクエリ呼び出しに属する派生実体、interned struct が不変値の正準化を担い、tracked function が自身の読んだクエリを記録して無効化境界として機能する。純粋関数で非巡回であることを前提とする。

名前解決については **Scope Graphs (Néron / Tolmach / Visser / Wachsmuth, ESOP 2015)** が理論を与えている。参照・宣言・スコープをノードとし、解決計算が参照から宣言へのパスを規定する。曖昧参照は「同じ参照から始まる複数の解決パス」、未解決参照は「解決パスの不在」として自然に対応する。

我々の requires / provides はこの参照 / 宣言と同型である。「未解決参照を即時エラーとせず保持する」という要件も、Scope Graph では第一級の状態として既に扱われている。

### 4.5 関係付き ECS

**flecs** の relationships 機能が、ECS でエンティティグラフをネイティブに記述可能にしている。単方向関係へのクエリはすべて定数時間。2021 年の導入以降、他の ECS 実装も追随している。

ただし flecs では関係ごとに個別のアーキタイプが作られ、リンクごとにヒープ上で約 1000 バイトを消費するという指摘がある。数万個の数式エンティティを扱う場合のメモリ特性は事前検証が要る。v0.1 では ECS ライブラリを使わない判断をした（§9 ADR-002）。

### 4.6 バックエンド

**CortexJS Compute Engine (CCE)** は既に宣言・代入・仮定の機構を持つ。`["Declare"]` が現在スコープにシンボルを宣言し、`["Assign"]` が値を変更する。Assign はスコープを親方向に辿って定義を探し、型が互換なら値を変更する。`["Assume"]` で「この変数は正である」といった述語を与えられる。

**ただし、一度設定されたシンボルの型は変更できない**。「シンボルの型が変わると意味解釈も変化する」という我々の要件と正面から衝突する（§7 R4）。

### 4.7 検索した範囲で見つからなかったもの

ECS のデータレイアウト上に数学オブジェクトを載せ、requires / provides から依存を導出する実装は見つからなかった。MMT は理論グラフ、salsa はクエリグラフ、Pluto は変数参照グラフで、いずれも ECS ではない。

**「見つからなかった」であり「存在しない」の証明ではない**。また率直に言えば、ECS であること自体は本質的な差分になりにくい。ECS の価値はキャッシュ効率と動的合成にあり、数万個程度のエンティティではどちらもボトルネックにならない。差別化の主張を ECS に置くべきではない。

## 5. 差別化 — 検証可能な仮説として

第2版の差別化表は主張であって検証手段がなかった。ここでは検証可能な仮説に書き換える。

### H1: 定義変更時の再検証コストが下がる

**主張**: 定義を 1 箇所変えたとき、人が確認すべき箇所の数が、既存手段より少なくなる。

**測り方**: 教科書の演習問題を 10 題選び、各題を（a）紙、（b）Jupyter、（c）本システムで解く。その後、各題の前提を 1 箇所変更し、正しい結果に到達するまでに人が触った箇所の数を数える。

**成功水準**: (c) が (b) の 50% 以下。

**失敗した場合**: 偽陽性が多すぎる可能性が高い。早期カットオフの粒度を見直す。それでも下がらなければ、依存追跡の価値仮説そのものが疑わしい。

### H2: 意味マクロが型情報から正しく解決される

**主張**: `\norm{v}` が `v` の型宣言に応じて `Abs` / `VectorNorm` / `MatrixNorm` に解決される。

**測り方**: 型が異なる 20 ケースを用意し、解決結果を確認する。

**成功水準**: 20/20。型未指定の場合に「型を指定してください」と言えること。

**失敗した場合**: 型情報が式の評価結果に依存するケースで循環する（§7 R1）。その場合、意味マクロは宣言済みの型のみを見る、と制約する。

### H3: LaTeX より入力コストが高くならない

**主張**: 同じ数式を入力する時間が、生の LaTeX を書くのと同程度以下である。

**測り方**: 10 個の数式について、MathLive での入力時間と LaTeX 手打ちの時間を計測する。

**成功水準**: 中央値で LaTeX の 1.2 倍以内。

**失敗した場合**: これは致命的である（§7 R5）。どれだけカーネルが優れていても、入力が苦痛なら誰も使わない。

### H4: 同一 IR から複数バックエンドへ変換できる

**主張**: 意味・型・評価戦略を持った IR から、SymPy と数値計算の両方に、意図通り変換できる。

**測り方**: `\int_0^1 x^2 dx` のような、記号積分と数値積分で結果の意味が変わる式を 15 個用意し、評価戦略の指定に応じて正しい方に振り分けられるか確認する。

**成功水準**: 15/15。

## 6. アーキテクチャ

```
フロントエンド UI（数学ワークスペース）
  ↓
MathLive（数式入力）
  ↓
CCE parse → MathJSON
  ↓
ホスト層（IR 生成・requires/provides の抽出）
  ↓
Relational Math Kernel  ← 本プロジェクトの中核
  ↓
バックエンドアダプタ
    CCE / SymPy / Python / SageMath / NumPy / SciPy / Lean / 可視化
```

### 6.1 層の責務

| 層 | 責務 | 知らなくてよいこと |
|---|---|---|
| UI | セル編集、状態表示、依存表示 | SymPy や Lean の事情 |
| ホスト | パース、IR 生成、requires/provides の決定、評価の実行 | — |
| カーネル | 依存追跡、鮮度管理、再計算順序 | 数式の中身、評価方法、I/O |
| アダプタ | IR → 各バックエンドの表現 | UI のセル構造 |

### 6.2 カーネルが requires を推測しない

重要な制約である。**カーネルが式の中身をパースして依存を推測することは禁止する**。requires は必ずホストが明示的に登録する。

理由は §4.3 の IPyflow の失敗モードである。解析で依存を推測する系は、解析の限界がそのまま健全性の穴になる。明示登録にすれば、穴はホスト層に局在し、カーネルは常に正しい。

### 6.3 評価はホストが行う

カーネルは `next_batch()` で「今すぐ再計算可能なエンティティ」を依存順に返す。ホストがそれを評価し、`commit_evaluation()` で結果のダイジェストを報告する。

これによりカーネルは純粋・同期・I/O なしになり、テスト可能性が大きく上がる。

## 7. リスク登録簿

第2版になかった節である。技術的難所を明示し、担当と対応方針を決める。

### R1: 意味マクロの解決と型推論の循環 — 影響度 高 / 確度 中

`\norm{v}` の解決には `v` の型が要る。`v` の型が計算結果から決まる場合、解決と評価が循環する。

**対応**: v0.1〜P3 では、意味マクロは**明示的に宣言された型のみ**を見る。型推論の結果は見ない。制約が厳しすぎることが分かったら、その時点で型推論を段階化する設計に進む。

### R2: バックエンド間の意味不一致 — 影響度 高 / 確度 高

`sympy.integrate` と `scipy.integrate.quad` は違うものを返す。前者は記号式、後者は数値と誤差である。同じ入力式から両方に変換できることは、両者が交換可能であることを意味しない。

さらに深刻なのは、§4.3 が示した通り、Python バックエンドを繋いだ時点でミューテーションと外部効果の世界に入り、カーネルの依存モデルが健全性の保証にならなくなる点である。

**対応**: IR に評価戦略（記号 / 数値 / 要求精度）を第一級で持たせる。バックエンドを「純粋な関数」と仮定するのか汚染を追跡するのかを、P1 の設計時に明示的に決める。v0.1 の非目標であることを守る。

### R3: 偽陽性 dirty — 影響度 中 / 確度 高

§4.2 の通り、可能性ベースの伝播は必ず偽陽性を生む。偽陽性が多いと「どうせ全部再計算」になり、価値が消える。

**対応**: 早期カットオフを後付けにせず、カーネル v0.1 の M5 で必須実装とする（要件定義書で規定済み）。H1 の測定で偽陽性率を継続的に見る。

### R4: CCE の型変更不可制約 — 影響度 中 / 確度 高

CCE は一度設定されたシンボルの型を変更できない。我々は型変更を扱いたい。

**対応**: 3 案ある。(a) 型変更のたびに CCE のスコープを作り直す、(b) CCE インスタンスを捨てて再生成する、(c) 型変更を「別 Entity の再登録」として扱う。カーネル側は (c) を採用済み（ADR-005）。CCE アダプタ側の方針は P1 で決める。

### R5: 入力コストが LaTeX を上回る — 影響度 致命的 / 確度 中

どれだけカーネルが良くても、数式の入力が苦痛なら使われない。数学ツールの墓場はここにある。

**対応**: H3 を P2 のゲート条件にする。基準を満たさなければ P3 に進まない。

### R6: 想定利用者が実在するかの不確実性 — 影響度 致命的 / 確度 中

「LaTeX 並みに書きやすく Pluto 並みに反応する」位置が空いている理由が、需要がないからである可能性を排除できていない。

**対応**: P2 完了時点で、開発者以外の実利用者を 5 名確保して 2 週間使ってもらう。継続利用率を見る。

### R7: スコープ膨張 — 影響度 高 / 確度 高

第2版の時点で、MVP に積分・行列・型宣言・マクロ・複数バックエンドが入っていた。全部やろうとすると全部終わらない。

**対応**: §11 の非目標を各フェーズで明示的に再確認する。要件定義書の受け入れ基準に「非目標の機能が 1 つも入っていない」を含めた。

## 9. 決定記録（ADR）

口伝になっていた決定を記録する。実装者はこれらを再検討しなくてよい。

### ADR-001: 実装言語は Rust

**決定**: カーネルは Rust で実装する。

**理由**: (1) 状態機械と所有権の相性が良い、(2) salsa をはじめインクリメンタル計算の実装例が豊富、(3) WASM で将来フロントに載せられる、(4) 実装者の習熟。

**代替案**: TypeScript（フロントと同一言語だが、性能と型の厳密さで劣る）、OCaml（言語処理系向きだが実装者が少ない）。

**再検討条件**: 要望があれば変更する。ただし P0 完了後は移行コストが高い。

### ADR-002: v0.1 では ECS ライブラリを使わない

**決定**: bevy_ecs / flecs 等を使わず、`HashMap<Entity, T>` で実装する。ただし storage はトレイト越しにし、後日差し替え可能にする。

**理由**: 想定エンティティ数（〜10^4）ではアーキタイプ storage の利点が出ない一方、関係ごとのアーキタイプ断片化はメモリコストになる（§4.5）。

### ADR-003: 依存グラフは一次データにせず導出する

**決定**: `requires` / `provides` を一次データとし、依存グラフはそこから導出する。ただし増分保守する。

**理由**: 依存を直接持つと、式の変更と依存の更新が二重管理になり、整合性を保つ責任がホストに漏れる。

### ADR-004: カーネルは評価しない

**決定**: 評価はホストが行い、結果のダイジェストをカーネルに報告する。

**理由**: カーネルを純粋・同期・I/O なしに保つため。テスト可能性が劇的に上がる。オラクルとの等価性テスト（要件定義書 P1）はこの決定なしには書けない。

### ADR-005: 型変更は別 Entity の再登録として扱う

**決定**: 「同一 Entity の型更新」という操作を用意しない。

**理由**: CCE が「一度設定されたシンボルの型は変更不可」という制約を持つため、カーネル側でこれと矛盾する状態を作らない（§7 R4）。

### ADR-006: 循環はエラーにせず in_cycle フラグで表現する

**決定**: 循環依存を検出したらフラグを立て、`next_batch()` の対象外にする。エラーにはしない。

**理由**: `y = f(x)` と `x = g(y)` は数学的には正当な連立方程式である。ただし v0.1 のカーネルは求解を担わないため、扱いは上位層に委ねる。

### ADR-007: v0.1 はスコープを持たない

**決定**: 単一グローバル名前空間とする。シャドーイングを扱わない。

**理由**: スコープを入れると Scope Graph 相当の解決計算が必要になり、v0.1 の規模を超える。

### ADR-008: 意味マクロは展開しない

**決定**: `\norm{x}` を `\left\lVert x \right\rVert` に展開せず、`Norm(x)` として保持する。

**理由**: 展開すると意味が失われる。ノルムなのか単なる縦棒表示なのか区別できなくなる。

## 10. マクロの分類

マクロを 4 種に分ける。第2版から維持するが、ADR-008 との関係を明示する。

| 種別 | 例 | 扱い |
|---|---|---|
| 表示マクロ | `\newcommand{\RR}{\mathbb{R}}` | 展開してよい |
| 構文マクロ | `\newcommand{\sq}[1]{#1^2}` | 展開してよい |
| 意味マクロ | `\DeclareMathFunction{\norm}[1]{Norm(#1)}` | **展開しない**。IR に `Norm(x)` として保持 |
| 変換マクロ | `Norm(x)` → SymPy / NumPy / Lean での表現 | アダプタ層に登録 |

意味マクロもカーネル上の Entity として扱える。これにより、マクロ定義の変更がそれを使う数式セルの意味状態に波及することを管理できる。

| 資産 | 位置づけ | 使う機能 |
|---|---|---|
| MathLive | 入力 UI 基盤 | Mathfield、仮想キーボード、LaTeX / MathML / MathJSON 入出力 |
| CCE | 構造化基盤 + 第一バックエンド | LaTeX ↔ MathJSON 変換、記号 / 数値評価、Declare / Assign / Assume |

いずれも**競合ではなく基盤または接続先**である。MathLive / CCE を再実装するのではなく、その上にカーネルとワークスペース UI を作る。

ただし、MathJSON だけでは足りない。独自の意味マクロ、ドメイン情報、requires / provides、バックエンド変換規則を扱うには、カーネル側の意味層が要る。

## 13. 競合分析

第2版の 3 プロダクトに、§4 で見た系統を加えて再整理する。

| 対象 | 出発点 | 我々との差 |
|---|---|---|
| GNU TeXmacs | 科学技術文書エディタ / 組版環境 | 我々の出発点は組版ではなく、定義・型・依存・鮮度の管理 |
| KDE Cantor | 複数バックエンドのワークシート UI | バックエンドを束ねるだけでなく、実行前に意味状態と依存を管理する |
| MathPad | 教育・宿題・単問解決 | 単問解決ではなく、定義と補助式が積み上がる作業空間 |
| Jupyter | 汎用コード実行環境 | セル間依存を数学的意味として管理しない |
| Pluto.jl / marimo | リアクティブ実行 | 依存追跡は同じ。ただし数式表現と意味層がない |
| MMT / OMDoc | 形式数学の知識管理 | 証明系ではなく計算系を向いている |
| Mathematica | 統合数学環境 | 閉じた環境。バックエンド非依存でない |

**生成 AI との関係**: これは競合でもある。数学作業の入口として LLM を使う人が増えている。ただし LLM の答えは「もっともらしい説明」にはなりやすい一方、数学的に検証済みとは限らない。

したがって LLM は計算の本体ではなく補助に置く。入力補助、数式候補の提案、エラー説明、自然言語からセルへの変換補助、依存関係や未解決状態の説明。最終的な意味管理・依存管理・検証はカーネルと外部評価器が行う。
